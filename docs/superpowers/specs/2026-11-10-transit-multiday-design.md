# 国内の公共交通と日またぎの旅程

## 目的と現在の問題

国内の電車・バスを含む旅程を、実際の経路検索結果で作成する。終了日を指定し、日をまたぐ旅程を作成・編集・コピー・遅延時に再計算できるようにする。

公開サイトで確認した問題:

- 東京駅9:00発、大阪城を経由、新大阪駅17:00着は `END_INFEASIBLE` になる。
- 出発地を新大阪駅に変えると作成できるが、大阪城への移動が徒歩103分、往復205分になる。
- Google Routes APIは日本の公共交通を提供していない。現在の `Maps.Route` は公共交通の結果が空でも徒歩の結果を採用する。
- `end.arriveBy` は旅行日と同じ日の時刻として扱われる。画面・入力検証・営業時間・編集・遅延処理にも同日の制限がある。

利用者は「まず車・徒歩に対応する」案と「電車・バスにも対応する」案のうち、公共交通への対応を選択した。

## 方式の比較

1. Google APIで車・徒歩を扱う。新しい接続先を増やさずに済むが、利用者が選択した公共交通への対応を満たさない。
2. 国内対応の公共交通APIを使う。追加のアクセスキーが必要だが、電車・バスと駅までの徒歩を実際の経路から計算できる。この方向を利用者が選択した。
3. 所要時間をAIや直線距離から推測する。実際に乗車できる時刻を検証できず、到着できない旅程を保存することになるため採用しない。

接続先は実装者の提案として **mixway API（駅すぱあと系）** とする。座標間の公共交通検索と出発日時指定が公開仕様にあり、標準HTTPで実装できる。NAVITIMEも比較したが、契約形態ごとの時刻表オプションと、直接契約で別途提供される認証資料の確認が必要になる。今回は接続先を複数実装しない。

この設計の確認はソフトウェアの実装方針の確認であり、外部サービスの契約・課金・公開環境の変更を承認するものではない。

## 公共交通の経路検索

- Google Placesは施設検索・詳細・座標・営業時間の取得に使い続ける。
- 経路は `https://mixway.ekispert.jp/v1/json/search/course/extreme` を利用する。Google Routesの `TRANSIT` 呼び出しと、結果が空のときの暗黙の徒歩への切り替えを廃止する。
- `viaList` に始点・終点の世界測地系の緯度経度、`date` に日本時間の `YYYYMMDD`、`time` に `HHMM`、`searchType=departure` を渡す。
- 鉄道・バス・徒歩を含む経路を扱う。タクシー、航空機、船、シェアサイクルなどを代わりの交通手段として採用しない。除外パラメータと応答の扱いは公式仕様に従う。
- 実際の到着日時で候補を比較する。乗車までの待ち時間・駅までの徒歩・乗り換え・降車後の徒歩を所要時間に含める。最初の便の発車時刻と、利用者が出発する時刻を混同しない。
- 既存の `Leg` の `mode`、`durationMin`、`departAt`、`arriveAt`、`lineName` に変換する。鉄道を含む区間は `train`、バスのみの公共交通区間は `bus`、徒歩のみの経路は `walk`。路線名は取得できた実際の名称を使う。
- 徒歩だけの経路も、mixwayが正規の検索結果として返した場合には利用できる。公共交通の取得失敗を徒歩の検索成功と扱わない。
- 経路がないと明示された場合は422 `ROUTE_NOT_FOUND`。認証失敗・応答不正・通信失敗は502 `UPSTREAM_ERROR`、上流の429は既存の `RATE_LIMITED` とする。応答内のエラーを、経路なしと誤判定しない。
- `MIXWAY_API_KEY` が未設定の場合、経路を必要とするリクエストは503 `TRANSIT_UNAVAILABLE` と説明文を返す。他の施設検索APIは利用できる。同一地点の移動は従来どおり0分。
- APIキーはサーバーの環境変数で設定する。GoogleのADC付きHTTPクライアントはmixwayに共有しない。キー、認証情報、外部エラー本文を利用者に返さない。
- 外部HTTPは既存の15秒、リクエスト全体は60秒の上限を維持する。既存の経路キャッシュを使う。
- 施設の座標は既に取得したものを再利用する。経路を試すたびに同じ施設の詳細取得を繰り返さない。必要な内部データの持ち方は実装者が既存の `Waypoint` に合わせて決める。
- 料金やリアルタイムの遅延反映を新たに保証しない。AIで移動時間を補完しない。

## 日時のAPIと保存

既存の入力を受け付けるため、開始日はトップレベルの `date` のままとし、終了日の `end.date`（YYYY-MM-DD）を任意で追加する。

```json
{
  "date": "2026-11-20",
  "start": {"placeId": "start-place", "departAt": "23:00"},
  "end": {"placeId": "end-place", "date": "2026-11-21", "arriveBy": "01:00"}
}
```

- `end.date` の省略は開始日と同じ日を意味する。終了日時は開始日時より後でなければ400。日付文字列は厳密に検証する。
- 新しく作成・更新する旅程には解決済みの終了日を保存する。既存レコードの終了日欠落は開始日と解釈する。既存データの一括書き換えは不要。
- 予定と移動の開始・終了は既存どおりRFC3339の日時で保存・返却する。
- `end.date` が後の日なら、その日までの連続した旅程を作成できる。開始日への日付の巻き戻しを起こさない。
- 営業時間は到着日の曜日を基準にし、当日の営業に入らなければ終了期限内の次の営業区間を探す。前日から続く深夜営業と24時間営業も扱う。
- 宿泊・就寝時間・日ごとの活動時間帯を自動で作らない。施設数と各施設の滞在時間の既存の上限を変更しない。利用者が開始・終了を指定した1つの連続タイムラインとして扱う。
- 期限は終了日から30日とし、複数日の旅程が開始日を基準に早く期限切れにならないようにする。

## 作成以外の整合性

- 編集: 終了日の変更を受け付ける。開始日だけを移す編集では、終了日を明示しなければ元の日数を保って移す。完了済み・滞在中の予定は従来どおり固定する。
- 2日目以降の部分編集: 固定部分の実際の終了日時から残りを計算し、旅程自体の開始日は保持する。
- コピー: 元の開始日から終了日までの日数を保って移す。訪問順・滞在時間・優先度を引き継ぎ、状態は `upcoming` に戻す。
- 遅延: 2日目以降の `now` と、600分以内の遅延による日付越えを扱う。終了期限超過は既存の警告と案の選択で扱い、時刻を開始日に戻さない。
- 空き時間提案・予定追加: 旅程の開始日時と終了期限の間で受け付け、次の予定までの移動も検証する。開始日だけとの一致チェックを廃止する。
- AI: 開始・終了の両方の日時と、候補の営業区間を渡す。実際の経路・時刻の検証はサーバー側に残す。
- 一覧: 2日目以降も、その日のうちに予定が残っている旅程を「今日」に含める。表示の判断には実際の旅程終了日時を使う。

## Flutterの変更

- 作成・編集画面で開始日と終了日を指定できるようにする。開始日を変えたときは、現在の旅程の日数を保って終了日も移す。終了日は開始日以降から選択する。
- 出発時刻と終了時刻だけを比べるのをやめ、日付を含む開始・終了日時を比較する。
- APIの入力・応答モデルに任意の終了日を追加し、FreezedとJSONの生成ファイルはツールで再生成する。
- モックAPIにも同じ日付の契約を反映する。実APIとモックで日またぎの挙動を変えない。
- 旅程画面・組み直し案では、日が変わる箇所と終了日時に日付を表示し、同じ時刻の予定を別の日と識別できるようにする。
- 「1日ごとに旅程をつくれます」など、今回の機能と矛盾する文言を更新する。新しいエラーの説明文を表示する。

## 対象ファイルと構成

- `server/internal/service/maps.go`: 施設・座標取得と共通の経路呼び出しの接続。
- `server/internal/service/transit.go`（新規）: mixwayへのHTTPと既存のLegへの変換。汎用の複数プロバイダー層は作らない。
- `server/internal/service/firebase.go`、`server/.env.example`、`server/README.md`: 接続設定、利用準備、制限の説明。
- `server/internal/service/types.go`、`planner.go`、`items.go`、`replan.go`: 終了日と日付を保った計算。
- `server/api`のテスト、`server/internal/service`のテスト: 経路・入力・保存・再計算の回帰テスト。
- `app/lib/data/models`、`app/lib/data/api/mock_itinerary_api.dart`: 日付の受け渡しとモック。
- `app/lib/features/plan`、`today`、`replan`、`itineraries`と必要な表示・文言: 入力と複数日の表示。
- `app/test`: JSONの互換性、日またぎ入力、コピー、一覧の2日目分類など。

## 検証と完了条件

1. 公共交通の検索結果を返すHTTPモックで、東京から大阪への旅程が徒歩時間によって却下されない。
2. 鉄道・バス・徒歩、乗り換え待ち、日をまたぐ到着、不正JSON、キー未設定、上流エラー、経路なしを確認する。
3. 従来の同日入力が引き続き成功する。23時出発・翌1時終了の入力が成功し、終了日前後の逆転は400になる。
4. 翌日の開店待ち、深夜営業、日付をまたぐ移動を終了期限と正しく比較する。
5. 2日目の編集・遅延・空き時間提案、日数を維持するコピー、終了日基準の期限を確認する。
6. Goの通常テスト・race検査・vetと、Flutterのモデル生成・analyze・テスト・Webビルドを行う。既存環境の問題で実行できない項目は、実装の検証結果と分けて報告する。
7. 最後にコードを読み直し、不要な関数分割・抽象化・設定・コメントを減らす。

実際のmixway接続には利用者が用意するアクセスキーが必要。キーがなければ接続コードとモックでの検証までを完了し、公開サイトで直ったとは報告しない。契約・キー発行申込・課金設定・デプロイ・push・PR作成はこの実装の完了条件に含めない。
